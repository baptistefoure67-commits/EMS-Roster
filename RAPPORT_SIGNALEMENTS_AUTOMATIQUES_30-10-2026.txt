2. RÈGLES MÉTIER IMPLÉMENTÉES
============================================================

Grades éligibles :
MF, MP, MLP, RF, RP, RL, MC, ADD

Grades exclus :
STG, A, INF, M, CD, D, DG, OWNER

Une seule personne par événement.

Mode normal : tirage aléatoire parmi les employés :
- présents dans rosterEmsData ;
- non licenciés ;
- ayant actuellement un grade éligible.

Mode manuel :
- uniquement si session.level === "OWNER" côté serveur ;
- ADD/CD/D/DG sont refusés même avec une requête bricolée ;
- la cible est revérifiée côté serveur au moment final avant création.

Signalement officiel créé :
- category: "autre"
- reason: "Signalement automatique pour discuter avec cette personne."
- source: "automatic_payroll_check"
- selectionMethod: "random" ou "owner_selected" (privé)
- selectedBy: ID Discord OWNER uniquement si owner_selected (privé)

Aucun nouveau workflow de sanction n'a été ajouté.
Le signalement reste un signalement officiel normal et continue d'être traité
avec le système existant de Pillbox/Roster.

============================================================
3. COMPTEUR PERSISTANT
============================================================

Après une création, le serveur tire nextAutomaticReportIn entre 1 et 3.
À chaque nouvelle clôture de semaine :
- si > 1 : décrémentation et aucun signalement ;
- si = 1 : création puis réarmement aléatoire 1..3.

L'état est enregistré sous :
pillboxWeekHistoryArchive/__automaticPayrollSignalement/<production|test>/state

Ce chemin réutilise une branche Firebase déjà réservée aux fonctions serveur.
Aucune modification des règles Firebase n'a été nécessaire.

Chaque semaine est mémorisée pour rendre l'opération idempotente :
- un double clic ;
- une relance après panne ;
- une re-clôture de la même semaine
ne créent pas un deuxième signalement.

Le signalement utilise une clé stable :
automatic-payroll-YYYY-MM-DD

============================================================
4. ANTI-RÉPÉTITION
============================================================

Le dernier tiré reste possible, mais son poids est fortement réduit :
- dernier tiré : poids 0,15
- 2 précédents : poids 0,45
- autres : poids 1

Donc :
- aucune rotation fixe ;
- vrai hasard conservé ;
- répétition immédiate fortement réduite mais jamais impossible.

============================================================
5. CONFIDENTIALITÉ DU MODE DE SÉLECTION
============================================================

selectionMethod / selectedBy sont filtrés pour les non-OWNER dans :
- signalement-actions.js -> action listSignalements
- pillbox-proxy.js -> POST listSignalements
- pillbox-proxy.js -> réponse GET générale des signalements

Le Roster et Pillbox n'affichent jamais ces champs dans l'interface normale,
y compris pour OWNER.

OWNER peut récupérer l'état technique via l'action serveur interne :
getAutomaticPayrollSignalementDebug

Aucun log normal ne précise « choisi par l'Owner ».

7. BUG / RISQUE TROUVÉ EN COURS DE ROUTE
============================================================

Lors du premier design, rosterLogsHiddenTrace semblait être un bon emplacement
server-only pour le compteur. Audit du code : get-logs.js purge automatiquement
les entrées de cette branche selon createdAt. Un état technique placé dedans
aurait donc pu être supprimé en consultant les logs OWNER.

Correction AVANT livraison : état déplacé sous
pillboxWeekHistoryArchive/__automaticPayrollSignalement, qui est server-only et
n'est pas soumis à cette purge.
